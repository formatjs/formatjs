# Test262 progress — 2026-09-11

Temporal DateTimeFormat support removes 110 failing executions in each mode.
The twelve polyfills now record 2,422 passes from 2,498 executions (96.96%),
with 76 failures retained. DateTimeFormat itself improves from 330/488 to 440/488.
All upstream cases still execute; no failure was skipped or reclassified as a pass.
The remaining diagnostics are unchanged.

The Test262 pin remains `419d3e0a2273ba01a3bfcbec423f2801425b8e93`, with
checksum-pinned Node 26.8.1, CLDR 48.2, and IANA timezone data 2026c.
All 24 isolated/combined baseline gates passed with `--local_test_jobs=3`,
alongside six focused/package tests and the implementation/regression typechecks.
The native-control results in the main report remain the September 9 measurement.

## Changes

All four formatting methods recognize Temporal inputs through captured intrinsic
brand checks, including values from foreign realms. Type-specific formats use
already-read options. Plain values ignore the formatter's timezone; instants use
it. Numeric inputs retain TimeClip, while Temporal values preserve their wider
plain-date range. Range endpoints must have matching Temporal types and
compatible calendars. `ZonedDateTime` remains rejected as the specification requires.

Missing time interval patterns now get a time-only fallback before combining
with the shared date. This fixes same-day ranges that repeated the date, for both
Temporal and Date inputs. Existing CLDR interval patterns retain precedence.

Focused regressions cover poisoned getters, subclasses, foreign realms, options
read counts, range coercion order, calendar compatibility, negative submillisecond
instants, Date limits, and shared range parts. Package exports, declarations, and
generated locale validation also pass.
